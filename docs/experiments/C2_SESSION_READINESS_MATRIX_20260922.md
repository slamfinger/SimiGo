# C2 Controlled Lifecycle Matrix — Session Readiness\n\n**Date:** 2026-09-22  \n**Research Question:** Q_SESSION_READINESS_20260922  \n**Status:** PRE-REGISTERED / NOT YET EXECUTED  \n**Evidence channel:** C2 — controlled lifecycle matrix\n\n## 1. Purpose\n\nC2 is the controlled experiment specified by the Session Readiness research question. Its purpose is to test whether a minimal explicit readiness model can distinguish:\n\nABSENT → READY → RUNNING\n\nwith a failure/cancellation path:\n\nREADY/RUNNING → INVALID\n\nwithout requiring SimiGo to observe or own token-level Physical KV state.\n\nThis document defines the experiment before execution. It records neither a successful result nor a failed result.\n\n## 2. Current implementation boundary\n\nThe current runtime stores ManagedSession instances in state.sessions[executionKey.storageKey]. A new session is registered before generation/prefill completes. The existing protection for a newly created session uses the observed condition !reusedSession && rawEventCount == 0 on cancellation and evicts that session.\n\nThe existing code and incident record explicitly treat rawEv == 0 as a diagnostic/temporary criterion rather than a complete readiness model. The experiment therefore must not silently redefine rawEv as readiness.\n\nC2 must also preserve the V5.0 ownership boundary:\n\n- SimiGo may own logical session lifecycle and reuse eligibility.\n- Official ChatSession remains authoritative for Physical KV/token accounting.\n- C2 must not add a token ledger, KV state mirror, or second Physical KV authority.\n\n## 3. Experimental factors\n\nUse one fixed model, one fixed SimiGo build, one fixed MLX/mlx-swift-lm dependency pin, and one Apple Silicon device for a complete C2 run.\n\nVary only lifecycle outcome and whether the session was already reusable before the interruption:\n\n| Case | Session before request | Interruption/outcome | Required observation |\n|---|---|---|---|\n| A | absent/new | successful generation | new session becomes reusable only after the defined readiness point |\n| B | absent/new | cancel during prefill | session must not be selected for same-key reuse |\n| C | absent/new | generation failure before readiness | session must not be selected for same-key reuse |\n| D | ready/reused | successful generation | session remains reusable |\n| E | ready/reused | cancel during prefill | session handling must be observed; do not assume invalidation |\n| F | ready/reused | generation failure | session handling must be observed; do not assume invalidation |\n| G | ready/reused | normal completion after a prior cancel/failure | verifies whether the selected lifecycle result matches actual reuse behavior |\n| H | invalid/evicted | same-key request | a fresh session must be created rather than reusing the invalid object |\n\nCases E/F are deliberately not assigned an expected invalid state in advance. Historical evidence shows that cancellation of an already-reused session can enter an official rebuild path and complete successfully; therefore the experiment must distinguish “cancelled” from “invalid” rather than equating them.\n\n## 4. Repetitions\n\nFor each applicable case:\n\n- run at least 3 repetitions for the controlled matrix;\n- record every repetition independently;\n- if a case has timing-sensitive interruption, record the exact interruption point/trigger rather than grouping all cancellations together;\n- repeat the critical new-session cancellation case enough times to test for recurrence, with the same-key follow-up request immediately after each cancellation.\n\nThe exact repetition count may be increased for flaky timing, but additional repetitions must not be treated as independent evidence channels.\n\n## 5. Required trace observations\n\nFor every request record, where available:\n\n1. session key / execution key;\n2. whether an existing session was selected;\n3. reusedSession;\n4. rawEv / raw event count;\n5. whether generation reached a successful readiness point;\n6. cancellation/failure/completion outcome;\n7. whether the session remained in the session pool;\n8. whether the next same-key request reused it or created a new session;\n9. official cache/rebuild telemetry such as cacheEff, mode=rebuild, and processed token count, as observations only;\n10. any poisonedSessionEvict, reuseMiss, or lifecycle trace relevant to the transition.\n\nPhysical KV telemetry is recorded as observational evidence from the official runtime, not as a local readiness decision source.\n\n## 6. Primary acceptance test\n\nC2 supports H1 only if all of the following can be established from the controlled matrix:\n\n- a new session that has not reached the defined readiness point is never selected for same-key reuse after cancellation/failure;\n- a successful session can be classified as reusable without inspecting token-level Physical KV internals;\n- cancellation/failure of an already-reused session can be classified from lifecycle events without assuming “cancelled = invalid”;\n- same-key selection can be expressed as a readiness predicate rather than sessions[key] exists;\n- no second token ledger or Physical KV authority is required;\n- the observed behavior remains compatible with official ChatSession semantics.\n\n## 7. Falsification conditions\n\nTreat H1 as falsified or materially weakened if any of these occur:\n\n- reuse eligibility cannot be determined without token-level Physical KV facts that SimiGo would have to own;\n- a session that has clearly failed before readiness is later selected as reusable despite an explicit readiness predicate;\n- successful prefill/stream completion does not provide a stable logical readiness boundary;\n- normal production reuse requires an unready session;\n- an explicit readiness model necessarily duplicates official ChatSession lifecycle/cache authority.\n\nA single anomalous run is an observation to investigate, not automatic falsification; repeated reproduction under controlled conditions is required before changing the hypothesis.\n\n## 8.
