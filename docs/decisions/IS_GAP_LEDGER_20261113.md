# 信息空间缺口账：四项 → 五项（2026-11-13）

状态：当前口径 · 对应 issue #187 / #188 / #189

设置页那一行缺口数，是五个各自独立的数相加。原来只有四项，房间归属不在其中，
所以「缺口 0」不能读作「归属完整」。

## 五项与各自的口径

| 项 | 数的是 | 一句话口径 |
|---|---|---|
| 轮账 | 会话数 | `chat_messages` 有 `request_id`、但该会话没有 `chat_turn_ledger` |
| 摘要 | 轮数 | 账上有、`turn_digests` 没有 |
| 关键词 | 轮数 | 有摘要、词不够 |
| 时间 | 轮数 | 账上有、`source_time` 为空 |
| 房间 | 轮数 | 有摘要、但 `space_turns` 里没有任何归属 |

## 为什么归属要单算一项

增量归属（`assignTurnSpace`）在 `BEGIN IMMEDIATE` 里写 `space_turns`。全量重建或
补录持锁超过 `busy_timeout` 时它会抛 `SQLITE_BUSY`，此时**摘要和关键词已经落库**——
前四项一个都不变，失败的只有归属。前四项因此看不见这件事。

第五项排除「既无摘要也无归属」的轮次：那种轮次该由「摘要」那一项说话，两边都数
会让总数虚高。这与人工核对用的 SQL 同口径（`turn_digests` 里没有对应 `space_turns`
行的轮数）。

## 失败之后

- **先记欠账，再判归属**：写摘要与写「这一轮还欠一次归属判断」在同一个事务里。
  撞锁时要么两样都没落（那一轮还在摘要缺口里，看得见），要么摘要与待办一起落；
  不会出现「摘要落了、归属没了、连待办都没留」。
- 待办进 `space_assignment_retry`（`(session_id, turn_index)` 主键去重），进程重启
  后仍在；启动时与每次摘要写入都重放一次，成功即删行。
- 重试有两道限制：**次数**（默认 5 次，到顶不再自动重试、由 `abandoned` 报数）与
  **时间退避**（30s、1m、2m……封顶 30 分钟）。锁还在别人手上时记不下失败，那次
  尝试**不计数**——额度不会被连续几次摘要写入烧掉。
- 队列只管「记下来过的失败」。有摘要、没归属、又不在队列里的轮（工具补的摘要、
  早于队列存在的轮）由 `enqueueDigestsWithoutRoom` 补进队列；设置页的「重放」=
  补入队 + 重新武装放弃的行 + 重放一遍。
- 全量重建覆盖每条带摘要的轮次，收尾时清空待重试队列。
- 补录回执给每一轮失败一个名字（格式不合 / HTTP / 写库），让位与停止不计入失败，
  单独报「让位 N 次、停止于哪一轮」。
- 退避到点由 SimiGo 进程里的监视器叫醒（不是数据库自己调度）：启动与终止见
  [归属重试监视器](ROOM_ASSIGNMENT_RETRY_MONITOR_20261113.md)。
