## 三、怎么跑

```sh
python3 tools/backfill_turn_digests.py --limit 3     # 先量一次单价
python3 tools/backfill_turn_digests.py               # 全部（断点续跑）
python3 tools/backfill_turn_digests.py --session X   # 只跑一个会话
```

- 可重复跑：已有摘要的轮次自动跳过，中断后重跑不会重复计费。
- 一轮失败不拖垮整批；失败会打 `[fail]` 并留在"缺摘要"里，下次重跑会再试。
- 预期速度：单轮整轮 3.6–7 s，2545 轮约 2.5–5 小时。

## 四、投喂契约（脚本已实现，不要自己改）

| 项 | 值 |
|---|---|
| 问题上限 | 1200 字 |
| 回答投喂上限 | 1800 字（封顶） |
| 散文行 | 全留 |
| 每个代码块 | 前 6 行 |
| 声明行 | 最多 12 条 |
| 报错行 | 最多 8 条 |
| 另附 | `【代码概况】N 个代码块，共 M 行；声明：…` |
| 输出 | 只两行：`摘要：` / `关键词：` |
| 摘要长度 | ≤300 字（实际 100–130 字） |
| 关键词 | 5–8 个，每个 2–8 字 |

分层投喂成立的理由（实测）：长回答里代码占 86%–97%（≥15000 字时 97%），
语义全在散文里。245 个 ≥6000 字的轮次分层后中位 1007 字。

## 五、摘要写什么（这决定验收）

- 只写三件事：**这一轮要解决什么 / 结论是什么 / 哪件事明确没做**。
- 措辞跟原文一致：原文是提议就写"提出"，用户认可过才写"已裁定/已定"。
  **用户没认可的一律不许写成"决定"。**
- 不写"用户说/助手回答"这类套话，不抄原句。
- 不评价代码完不完整。提示词里已写明：这一层的代码你看不到、也不在摘要范围内；
  原文只要出现代码块，就说明这一轮把代码给出了。

## 六、验收

自动：`SELECT COUNT(*) FROM chat_turn_ledger l WHERE NOT EXISTS (SELECT 1 FROM turn_digests d WHERE d.session_id=l.session_id AND d.turn_index=l.turn_index);` 应为 0（或只剩已知失败轮次）。

人工：随机抽 10 轮，逐条对原文，看四件事——

1. 三要素在不在（解决什么 / 结论 / 明确没做）。
2. 有没有把"提出"写成"决定"。
3. 有没有"未提供完整代码""只给了片段""代码未全部显示"这类假话 —— 这是已知的唯一残留缺陷（6 轮验证里出现过 1 次，`t241`）。
4. 关键词能不能在原文里找到（以后要用它反查原文）。

## 七、已知边界

- 长文章（≥8000 字且代码 <20%）：没有代码块就退化成头尾各 900 字，撞 1800 封顶。这类轮次存在，摘要会漏中段。
- 数字/参数不进摘要是设计：IS 只存归一化索引，要具体数值就回原文取。不要为此改投喂。
- 不要让模型自己做压缩（让它把回答压成主谓宾那一路，实测 34 s/轮，还把 `compileBitcode = false` 写成"Bitcode 启用"）。
- 摘要不进 ES 结算，所以同一轮跑第二遍仍是全量 prefill，不会复用。
- `turn_digests.created_at` 是「2001-01-01 起秒数」的 `%.17g`，不是 Unix 秒。
- 库被 App 持有时写入可能忙：脚本已设 `busy_timeout=30000`。

## 八、出问题看哪里

`~/.simigo/logs/native_mlx_trace.log`

| 行 | 含义 |
|---|---|
| `[MLX] prefill a/b` | a<b 表示复用了前缀；a=b 是全量 prefill |
| `ttft=NNNms` | 首包。成本模型 ttft ≈ 78 + 0.815×prefill千tokens |

| `[IS_REUSE] … model_calls=0` | 结算复用（**摘要不该出现这个**，它不进结算） |
