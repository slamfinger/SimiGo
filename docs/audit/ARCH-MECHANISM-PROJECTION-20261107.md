## 2. 两条结构性结论（本文的主要产出）

### 结论 1：M1 与 M4 是同一个缺失对象的两面，应合并为一个审核对象

- 论据：`B新-2` 说「三个权威在 schema 层没有对齐机制」，`D-6`／`B新-1` 说「非成功终态没有任何持久承载体，
  也没有任何补偿链」。这两句话指向**同一张不存在的表**：一个同时枚举 `committed / settled / lineaged /
  summarised` 与 `failed / cancelled / detached / crashed` 的**执行终态权威**。
- 同一性由 `V-7` 直接证成：那个半状态之所以是**语义不一致**而非静默失败，正是因为
  IS 看 `committed` 就放行检索、settlement 与 ES 却不承认该轮完成 —— 判据分裂；
  而崩溃／取消／detach 之所以无从恢复，是同一位置**没有失败态的行**。一个对象缺了两种状态集合。
- 因此审核时应合并的只有**对象设计**（终态权威由谁承载、谁能写、谁读它做资格判定），
  **不应合并的是语义枚举**：detach ≠ cancel ≠ fail ≠ crash 各自应产生什么事实，属 M4 私有子问题，
  不能从 M1 的权威模型里自动推出。
- 收益：合并后 `D-1`／`D-2`／`D-5`／`D-6`／`D-8`／`A-9`／`B新-1`／`B新-2`／`B新-3`／`A新-4` 这 10 条
  不再是 10 项任务，而是**同一个设计决策的 10 个观测点**。

### 结论 2：owner 列的五簇不覆盖「外部文件世界 → IS」的失效与新鲜度传播，需要第 6 簇或明确暂不收敛

- 落空条目：`B-8`（无文件监听，`invalidateSourceFile`／`reconcileRoot` 产品零调用 ⇒ 运行时自动失效未实现）、
  `B-10`（`legacy-v1` 结算失效作用域为全库而非单根）、`F-C`（同结果集三个不同 `result_sha256`）、
  `R-5`（`settleWorkRootContents` 在 `BEGIN IMMEDIATE` 内做全树 IO）、`R-7`（大根扫描对首启与 HTTP 延迟的影响），
  以及冻结记录里仍列「未核验」的两项：`EnvManager.swift:542` 与 `:840` 两条注册入口的写集等价性、
  `indexExternalFile` 首建根 `display_name IS NULL` ⇒ `category:"model"` reconcile 时全计入 `unlocatableRoots`。
- 为什么它不是 M1 的子集：M1–M5 的对象全部是**轮次／分支／工具调用**，生命周期由产品自己发起；
  M6 的内容权威在产品进程之外 —— 外部文件可以被别的东西改掉，而 IS 里那条记录不会知道。
  这条方向上唯一已接通的入口是**手动**的（`/reconcile`），且两个入口不等价
  （MCP `simigo_is_reconcile` 不接 `max_age_seconds`、响应缺 `unlocatable_roots`，属已记 C-NEG）。
- 关联：本簇正是既有**待裁项 #28** 的落点。所以给 owner 的选择不是「要不要加一簇」，而是
  「M6 现在进入架构审核，还是显式记为暂不收敛并保持 #28 待裁」——后者同样是一个正当决定，
  因为 M6 与 M1/M4 的耦合最弱（只通过 `F-B` 的身份链间接相连）。

### 辅助结论（供选点，不构成优先级）

- **`D-11` 是唯一同时属 M2∩M3、且已有可测后果的条目**（GGUF 受管入口丢弃 agentId／sessionId／
  logicalBranchId，是 #90 冷 prefill 的代码根因）。若从「一个条目照亮两个簇」的角度选起点，它是最经济的一个。
- **阻塞关系**：`V-1`＋`V-2` 阻塞 M3 的结论（M3 主项只有 3 条，其余全是运行时缺口）；
  `R-6` 决定 M5 中 `A-10` 的严重性；其余 Ⅲ 类条目**不阻塞**任何簇的架构审核。
- **M2 是其他簇的依赖**：`F-B`（身份缺失→幂等失效→IS 写集无界）、`B-9`（分支命名空间与主体无绑定）、
  `A-9`（空身份条件才触发的静默断裂）、`D-10`（转正不校验身份）四条分别落在 M6／M5／M1／M2，
  但根因同形。这使 M2 更像**前置层**而非并列项。

## 3. 两个横切机制：解释问题为什么「反复出现」

owner 的中央问题是「怎样的产品执行模型能让已发现的问题不再反复出现」。审计材料里有两个反复出现的**产生机制**，
它们不是第 6／第 7 簇（不是设计对象），而是新代码会继续掉进去的形状：

- **X1 已实现但未接线。** 7 条：`D-5`（无对账或回收站点）、`D-6`（`recordFailureAudit` 产品侧唯一调用点是 MCP
  一个工具，六条 wire 零调用）、`D-9`（`reportOrphans` 产品零调用）、`A-11`（`branchGenerationMismatch` 零生产者）、
  `B-8`（`invalidateSourceFile`／`reconcileRoot` 产品零调用）、`B新-1`（无 repair／reconcile／invalidate 链）、
  `B新-3`（`settleContinuation` 公开、单事务、已测试、零产品调用者）。
  共同形状：**原语、状态列或错误类型都在，缺的是「谁必须调用它」的主体**。
  ⇒ 架构审核若只设计对象而不指认唯一调用主体，X1 会继续再生。
- **X2 失败被降级为无事实。** 5 条：`D-1`（`try?` 返回值与错误都不检查）、`D-8`（`_ = try?`）、
  `A新-5`（绑定抛错被上层 `try?` 吞）、`A-9`（静默 `return`，无 `[SETTLE_SKIP]` trace）、`A新-3`（描述面与实现矛盾）。
  共同形状：**异常路径不产生任何可查询事实**，因此不可观测、不可补偿。
  ⇒ 与 X1 合起来看，对中央问题的候选答案形状是三条约束，而非三个模块：
  ①一个执行终态权威对象；②每个权威有唯一调用主体；③失败必须成为事实。
  **此为假设，供架构审核检验，本轮不作裁决。**
