# SimiGo-Lab 档案体系设计来源与取舍

> 本文记录 SimiGo-Lab 档案体系借鉴的开源项目组织思想、实际采用方式及明确不采用的部分。
> 它是档案架构的设计记录，不是实验结论，也不改变任何研究状态。

## 1. 设计目标

SimiGo-Lab 的档案体系服务于研究过程，而不是产品运行时工程。核心目标是：

- 让研究问题、假设、实验、证据、发现、决策和不变量之间可追溯；
- 让已封存、已关闭、冻结、开放和未立项状态清晰分离；
- 保留历史资产的原始位置、身份和 Git provenance；
- 支持单人工作与未来多 Agent 异步协作；
- 允许研究线并行存在，但禁止未经裁定的跨线推理。

## 2. 参考来源与借鉴点

### 2.1 MLX 类项目的知识分层

借鉴点：通过 README、概念/架构说明、API 或实现说明、示例与测试，形成从入口到细节的渐进式阅读路径。

在 SimiGo-Lab 中的采用：

- 根目录 README 负责说明实验室定位与入口；
- `docs/00-governance/` 负责规则、状态和档案约束；
- 研究问题、证据、发现和决策采用分层目录；
- 实验目录保留为工作区，不强行改造成纯文档目录。

不直接照搬：SimiGo-Lab 不以 API 文档或产品使用说明为中心，研究状态与 provenance 优先级更高。

### 2.2 llama.cpp 类项目的工程协作链

借鉴点：问题提出 → 讨论/设计 → 实现 → 审查 → 测试/基准 → 合并或关闭的过程可见。

在 SimiGo-Lab 中的采用：

- 研究问题必须先形成定义和边界；
- 设计修订、外审、实验和 closure 分别留下记录；
- 结论不能仅由讨论文本或单次运行日志替代；
- Git commit、文档锚点和状态变更共同构成 provenance。

不直接照搬：研究实验不等同于普通功能 PR；通过代码合并不能自动证明研究命题成立。

## 3. SimiGo-Lab 的核心证据链

```text
Research Question
    → Hypothesis / Registered Prediction
    → Experiment Design
    → Evidence
    → Finding
    → Decision
    → Architecture Consequence
    → Invariant / Closure
```

其中每一段都必须区分：

- 计划与实际；
- 预测与结果；
- 观察与解释；
- 开放状态与封存结论；
- 当前研究线与另行限定的相关研究线。

## 4. 设计取舍

1. **先建索引，后迁移文件。** 第一阶段不大规模移动既有资产，避免破坏历史链接和路径语义。
2. **当前状态与历史记录分离。** `RESEARCH_STATE.md` 保持当前权威快照；历史论证进入专题文档与 Git 历史。
3. **实验工作区与档案索引分离。** `track-*`、`exp-*` 和 skeleton 目录继续承载实验材料，档案层负责索引和关系说明。
4. **不把候选思想自动升级为研究问题。** 记忆、假设、候选线索必须保持原有状态词汇。
5. **不以目录变化替代研究裁定。** 档案重构只改善可发现性与追溯性，不改变实验结论、状态或研究门禁。

## 5. 维护规则

- 新增档案目录或状态词汇时，先更新本文件或治理索引；
- 任何历史文件迁移必须保留旧路径映射和 Git provenance；
- 任何结论性链接必须指向具体 endpoint、closure、ledger 或 commit 锚点；
- 若档案结构与 `RESEARCH_STATE.md` 冲突，以研究状态文件和 Git 事实为准，并登记修复原因。
