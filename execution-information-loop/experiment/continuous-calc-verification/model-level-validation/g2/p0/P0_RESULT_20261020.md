## 2. Root cause

`EngineModelIdentity.compute` (`simigo2-experimental/Sources/SimiGo2Experimental/EngineSessionBaseline.swift:246`)
walks the model directory and keeps an entry only when
`resourceValues(forKeys: [.fileSizeKey, .isRegularFileKey]).isRegularFile == true`. For a symlink,
`isRegularFile` is `false` — it describes the link, not its target. Every file in a Hugging Face
snapshot directory is a symlink into `../../blobs/`.

Measured on this artifact (`20261020T072607Z-analysis/identity_enumeration.json`, no model loaded):

```
entries_yielded       17
is_regular_file_true   0
is_symbolic_link_true 17
weight_lines           0
weights_digest        e3b0c442…b855   (= SHA-256 of the empty string)
tokenizer_bytes        0
```

So the identity reader never opens a byte of this 17.2 GB artifact. The 0.0008 s duration recorded
in the probe is the tell: nothing was read.

The runner's prediction (`d1f01c0c…`, derived from the binding's 17 per-file digests, which follow
symlinks) and the engine's reading (`e3b0c442…`) are therefore two different measurements of the
same directory. Neither is a bug by itself; they disagree because the binding describes content and
the engine describes link entries.

## 3. Consequence for the frozen design

`MLXPrefixCrossSessionCache.namespace(modelID:contentIdentity:)` builds the KV fingerprint as
`chat-cross-session-v1-<combinedDigest>`. With both component digests empty, `combinedDigest` is a
constant:

```
sha256("weights:e3b0c442…\ntokenizer:e3b0c442…") = 188a16c59bd1407be74e57c04e46e20b7dd9f54b2582d91391d0b01d727c0938
```

which is exactly the fingerprint this run recorded. For **any** symlinked snapshot directory the
namespace fingerprint is that same constant; model separation then rests only on
`namespace.modelID`, which here is the revision directory name. Pre-registration §2.1 describes the
namespace as content-derived. On this layout it is not. Two different artifacts placed under the
same directory name would share a namespace, and the engine would not notice.

That does not invalidate G2-A by itself — the arm also requires process death, an empty store and a
canary — but it removes one of the four legs the design assumed, and it must be resolved before the
matrix can be frozen again.

## 4. Consequence outside G2 (observed, not adjudicated here)

The same function is the model-identity input for `EngineSessionBaseline` commits. For HF-cached
models, those commits therefore record an empty model identity. This record does not re-open V6,
F1 or F4; it reports what P0 saw, so that the finding is not rediscovered later as if it were new.

## 5. Amendment options (for a ruling; none is adopted here)

| Option | What changes | Cost / risk |
|---|---|---|
| **A1 — accept and re-scope** | Record that the engine namespace is path-scoped, not content-scoped, on symlinked layouts; G2-A leans on process death + empty store + canary + path binding | no new code; the "content-derived namespace" sentence in §2.1 must be withdrawn, and the negative control weakens |
| **A2 — resolve the artifact** | Run against a dereferenced copy (`cp -RL`, identical bytes ⇒ identical per-file digests and the same aggregate `4c1bd759…`); engine identity becomes non-empty and equals the predicted `d1f01c0c…` | +17.2 GB disk; the binding must be amended to name the resolved directory; not yet verified |
| **A3 — repair the reader** | Make `EngineModelIdentity` follow symlinks | library change with blast radius into baseline identity, F1/F4 and stored evidence; needs its own gate |

A2 preserves the design's content binding without touching library semantics, but it is a design
change and needs its own recorded amendment before any execution. A1 is the cheapest and the most
honest about what the engine actually measures, at the price of a weaker G2-A.

## 7. Runner defect (disclosed, fixed)

The parent wrote `run.log` and then crashed computing `os.getpgid(child.pid)` after the child had
already been reaped. Consequences: `launch.json` is absent, and the child's exit code was not
captured. The child's own records were unaffected — `P0_PROBE.json` carries `pid`, `process_group`
and both generation records, and `RUN_VERIFICATION.json` was re-derived afterwards from the files
by `run_p0.py --verify-only`, which agrees with the child's terminal (`verdict_agrees: true`).
`run.log` exists and is empty: the child printed nothing.

The fix (capture the pgid immediately after `Popen`; a `--verify-only` path that re-derives the
verdict without launching) is in the same commit as this record. It cannot recover the lost exit
code, and no attempt was made to reconstruct it.
